# @scripturetips/db

The PostgreSQL schema (Drizzle), its migrations, the connection, and databases for integration tests. So far: scripture text (domain-model §2): `translation`, `translation_book`, `verse_text`, `translator_note` (§2.6) and `translation_import`. Loaded by `tools/scripture-import`. Accounts (domain-model §5) in the shape Better Auth expects: `user` (with `handle`, `locale`, `trust_level`, `country` as a code from `@scripturetips/countries`), `country_claim` (a person's claim that their country isn't on the list, in their words, `pending` until a review that isn't built yet; never shown to anyone, one per account), `session`, `auth_account` (Better Auth's "account", renamed so it isn't mistaken for the user's account) and `verification` (sign-in codes, hashed). Compilations (domain-model §2.3): `compilation` (owner, slug unique per owner, title, abbreviation, base translation, scheme) and `compilation_rule` (kind, canonical `scope` range, the reference as entered, source translation), deleted with their compilation; `compilation_verse` (single-verse choices, edits with the source snapshot, and the user's own or pasted wording) , `compilation_note` (a source note reworded or removed, or the user's own note, on a compilation verse) and `compilation_verse_revision` (every save and reset, with the notes); `compare_shown` (the translation each verse was last shown in, in a user's compare view; deleted with the user, the compilation or the translation). Authorship evidence (§2.3.1): `authorship_journal` (one per writing session, with its start text, current text and chain head), `composition_event` (hash-chained bursts of writing, with paste origin), `study_trail`, `similarity_report` and `authorship_declaration`. Publish requests (§1.4): `publish_request` (scope, consent statement version and time, status, problems, warnings, review, and the version it made). Publications (§2.3): `publication` (public ID, owner, slug unique per owner, visibility, status, base and scheme; kept if its compilation is deleted), `publication_version` (public ID, number, meta, change note and summary, content hash chained to the previous version's) and `publication_chapter` (a version's verses, a chapter per row, with its hash). Original-language data (domain-model §2.4, loaded by `tools/original-import`): `source_text` (TAHOT, TAGNT), `lexicon` and `lexicon_entry` (Strong's, BDB, Abbott-Smith, hung from base lemmas), `lemma` (one per Strong's number, with STEPBible's extended lemmas pointing to it), `proper_name` (TIPNR), `token` (every Hebrew and Greek word, in the source's numbering with a canonical range) and `translation_alignment` (a translation's Strong's-tagged word, its lemma and token). The index also re-exports Drizzle's query helpers (`eq`, `and`, `sql` …), so every package uses this one copy of Drizzle and its types.

- **Schema changes go through migrations.** Edit `src/schema.ts`, then `./toolbox pnpm --filter @scripturetips/db generate <name>`, and commit the SQL in `migrations/`. Never edit a migration that has been applied; write a new one.
- **Keys are UUIDv7** (domain-model §1.1), made by PostgreSQL 18's `uuidv7()`.
- **Passages** are stored as canonical ordinal ranges (`int4range`, inclusive, from @scripturetips/passage) with a GiST index, so "what overlaps this passage" is one query.
- **Development database:** `./dev up` (on the host), then `./dev migrate` (it runs `pnpm --filter @scripturetips/db migrate` in the toolbox). The toolbox reaches it through `DATABASE_URL` (compose.yaml).
- **Integration tests** (testing.md §10) run on the `postgres-test` service, which starts with the toolbox and keeps its data in memory. Add `@scripturetips/db/test-support/global-setup` to a package's `vitest.config.ts`: each run migrates its own template database, and `testDatabase()` gives each test file a fresh clone.

Run the tests: `./toolbox pnpm --filter @scripturetips/db test`
