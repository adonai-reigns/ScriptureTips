# @scripturetips/web

The web app: Next.js (App Router), server-rendered, with next-intl for every user-facing string. So far: the landing page, the reader view, the credits page, sign-in with the account page, and the compilation editor. It reads scripture from the API (`API_URL`).

- **Reader view:** `/read/{translation}/{book}/{chapter}[/{verses}]` (domain-model §1.6), e.g. `/read/leb/genesis/2/18-25`, `/read/kjv/psalms/23`; several passages as `/read/{translation}/passage/joel.2.28,joel.3.1`. A book outside the reader's canon is labelled "Additional writings"; with no canon chosen, books the traditions disagree on are labelled as such (`@scripturetips/canon` `standing`). **Book list:** `/read/{translation}` lists the translation's books in the reader's canon order (`src/reader/books.ts`), each opening to its chapters; books printed inside another (Greek Esther) are listed with it. Each passage ends with previous and next chapter links in the same order. The search form posts to `/read?t=&ref=`, which reads the reference through the API and redirects to the canonical path.
- **Accounts** (`src/account/`): `/sign-in` asks for an email address and the ALTCHA bot check, then the emailed code; `/account` sets the handle, display name and canon profile, and signs out. Requests to `/api/auth/*` and `/api/account*` are proxied to the API (`next.config.ts`), so the session cookie belongs to the site the user sees. `currentAccount()` reads the account in server components; the header shows "Sign in" or the user's handle. Sign-in emails land in Mailpit: http://127.0.0.1:8025.
- **Compilations** (`src/compilations/`): `/compilations` lists the user's compilations and starts one (a handle is needed first); `/compilations/{slug}` is the editor: the choices with *Remove* (reset to inherited), a form to take a section or passage from another translation, the single-verse choices, each book's source (`sources.ts`), and deleting it. `/compilations/{slug}/verse?ref=` is the verse editor: the verse as the compilation has it, every translation's wording with *Use this*, a form to correct or adapt a translation's wording, and *Write your own rendering* (`OwnRenderingForm`: typing is sent to the authorship journal in bursts after a pause; pastes, undo and redo as their own events), with the declaration and, for a saved rendering, its evidence (record intact or not, declaration, similarity to each translation, the evidence download, and declaring a pasted one), and the verse's translator's notes (`NotesEditor`: reword, remove or restore a source's note, add, move or remove an own one); changing a note on a verse taken unchanged makes it a correction. Dates are held in UTC and shown in the browser's time zone (`LocalDate`, `src/dates.tsx`). The reader marks corrected verses †, adapted ones ‡, own renderings § and pasted ones *, and credits who changed which translation or wrote their own; a note adapted from a translation, or added in the compilation, says so in the notes list. Only translations whose license allows it are offered (`@scripturetips/licenses`). A compilation is read at `/read/@{handle}/{slug}/…` like a translation (`readerTarget`, `ownsCompilation` in `src/reader/paths.ts`), with a credit line naming its sources; `/api/compilations*` is proxied with the session cookie, and compilation requests are never cached. Someone else's compilation is not found.
- **Forms handled by script** keep their submit button disabled until the page has hydrated (`useHydrated`, `src/hydrated.ts`), so an early click can't submit natively and put the input in the URL. A controlled field (the verse editor's wording, the own rendering) is read-only until then, or text typed early gets mixed with the original or goes unrecorded.
- **The bot check needs a secure context** (HTTPS or `localhost`), since it uses Web Crypto. Plain HTTP on a network address, such as a phone on `./dev up --lan`, can read but can't sign in.
- **Rendering** (`src/reader/`): `layout.ts` lays verses out as printed (paragraphs and poetry lines running across verses, headings, verse numbers where each verse's text begins, verse 0 as a title without a number) and letters note marks in reading order, nested ones included. `Passage.tsx` draws it: idiomatic phrases in lower corner brackets, translator's notes listed below with links both ways.
- **UI strings** live in `messages/en-NZ.json` (New Zealand English). Errors from the API arrive as codes and are worded there.
- **Branding:** docs/branding.md. Assets in `public/brand/` (their rights: docs/license-evidence/ and the credits page). The artwork is the fixed page background; content sits on a plain panel over it.
- **Running it:** `./dev up` starts it with the API and database, with hot reload, at http://127.0.0.1:3000. `./dev up --lan` serves the web app to the local network too (to try it on a phone); `./dev up` again goes back to localhost only.
- **Tests:** unit tests (`*.test.ts`, in `pnpm verify`), and Playwright end-to-end tests in `e2e/` against the running stack: `./dev up`, then `./toolbox sh -c 'cd apps/web && npx playwright test'`. The browser opens the app as `localhost:3000`, mapped to the `web` container, so it counts as a secure context; the sign-in tests read the code from Mailpit. Shared steps (signing up, the bot check, screenshots, a separate client address per test) are in `e2e/support.ts`. They save desktop and phone screenshots to `test-results/screens/`; look at them for any UI change (definition of done). They aren't in `pnpm verify` yet, since they need the stack running.

Run the unit tests: `./toolbox pnpm --filter @scripturetips/web test`
