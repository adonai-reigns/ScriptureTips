# @scripturetips/web

The web app: Next.js (App Router), server-rendered, with next-intl for every user-facing string. So far: the landing page, the reader view, the credits page, and sign-in with the account page. It reads scripture from the API (`API_URL`).

- **Reader view:** `/read/{translation}/{book}/{chapter}[/{verses}]` (domain-model §1.6), e.g. `/read/leb/genesis/2/18-25`, `/read/kjv/psalms/23`; several passages as `/read/{translation}/passage/joel.2.28,joel.3.1`. The search form posts to `/read?t=&ref=`, which reads the reference through the API and redirects to the canonical path.
- **Accounts** (`src/account/`): `/sign-in` asks for an email address and the ALTCHA bot check, then the emailed code; `/account` sets the handle and display name, and signs out. Requests to `/api/auth/*` and `/api/account*` are proxied to the API (`next.config.ts`), so the session cookie belongs to the site the user sees. `currentAccount()` reads the account in server components; the header shows "Sign in" or the user's handle. Sign-in emails land in Mailpit: http://127.0.0.1:8025.
- **The bot check needs a secure context** (HTTPS or `localhost`), since it uses Web Crypto. Plain HTTP on a network address, such as a phone on `./dev up --lan`, can read but can't sign in.
- **Rendering** (`src/reader/`): `layout.ts` lays verses out as printed (paragraphs and poetry lines running across verses, headings, verse numbers where each verse's text begins, verse 0 as a title without a number) and letters note marks in reading order, nested ones included. `Passage.tsx` draws it: idiomatic phrases in lower corner brackets, translator's notes listed below with links both ways.
- **UI strings** live in `messages/en-NZ.json` (New Zealand English). Errors from the API arrive as codes and are worded there.
- **Branding:** docs/branding.md. Assets in `public/brand/` (their rights: docs/license-evidence/ and the credits page). The artwork is the fixed page background; content sits on a plain panel over it.
- **Running it:** `./dev up` starts it with the API and database, with hot reload, at http://127.0.0.1:3000. `./dev up --lan` serves the web app to the local network too (to try it on a phone); `./dev up` again goes back to localhost only.
- **Tests:** unit tests (`*.test.ts`, in `pnpm verify`), and Playwright end-to-end tests in `e2e/` against the running stack: `./dev up`, then `./toolbox sh -c 'cd apps/web && npx playwright test'`. The browser opens the app as `localhost:3000`, mapped to the `web` container, so it counts as a secure context; the sign-in tests read the code from Mailpit. They save desktop and phone screenshots to `test-results/screens/`; look at them for any UI change (definition of done). They aren't in `pnpm verify` yet, since they need the stack running.

Run the unit tests: `./toolbox pnpm --filter @scripturetips/web test`
