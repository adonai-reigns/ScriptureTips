# @scripturetips/api

The API: NestJS on Fastify, under `/api`. So far it serves translations and passages from the database (packages/db), accounts, and compilations.

- `GET /api/translations`: the translations that have text loaded.
- `GET /api/translations/{id}/passages?ref=Joel 2:28-32`: the verses of one or more references, read in the translation's numbering (@scripturetips/reference), each with its canonical passage, a display label, headings, markup and translator's notes (domain-model §2.6). At most `MAX_VERSES` (500) per request.
- `GET /api/translations/{id}/books`: the books with text, in registry order, each with its chapters (the reader arranges them by canon).
- **Accounts** (`src/auth/`, vision §11 "Sign-in"): Better Auth under `/api/auth/*`, mounted on Fastify by `AuthModule`. Sign-in is a one-time email code (6 digits, 10 minutes, 3 attempts, stored hashed) with **no passwords**; a new address becomes an account on its first sign-in. Asking for a code (`POST /api/auth/email-otp/send-verification-otp`) needs a solved ALTCHA bot check in the `x-bot-check` header, and is limited to 5 codes an hour per address and 60 requests an hour per IP. Then `POST /api/auth/sign-in/email-otp` sets the session cookie (30 days, renewed daily). Rate limits and spent bot-check solutions live in Valkey (`KeyStore`). Limits per IP read the client address from `X-Forwarded-For`, which the web app's proxy passes on: **in production the reverse proxy in front of the web app must overwrite that header with the client's address**, or clients could choose their own. Without it (as in development), every request shares one bucket; email goes over SMTP (`Mailer`, Mailpit in development).
- `GET /api/account/bot-check`: a bot-check puzzle. `GET /api/account`: the signed-in user (email, handle, display name, locale, canon profile, trust level). `PUT /api/account`: set the handle (once, for now; checked against domain-model §1.6 and a reserved list), display name (checked against the reserved names in any script) and canon profile (`@scripturetips/canon`, no default, changeable).
- **Compilations** (`src/compilations/`, domain-model §2.3), private to their owner: every route needs a session, and slugs are looked up among the signed-in user's own (someone else's is `unknown-compilation`, 404). `GET`/`POST /api/compilations` lists and creates (title, abbreviation, base translation); `GET`/`DELETE /api/compilations/{slug}`; `POST /api/compilations/{slug}/rules` adds a rule (`{scope: {section} | {reference}, source}`); `DELETE …/rules/{id}` resets it to inherited; `GET …/books` and `GET …/passages?ref=` read it like a translation. Each verse carries its `source` (and `edit`, `correction` or `adaptation`, where its wording was changed), and the result lists the `sources` to credit.
  - **Single verses:** `GET …/verses?ref=` shows one verse as the compilation has it beside every translation's that may be taken; `POST …/verses` (`{reference, source, text?, kind?, changeNote?}`) takes it from `source`, or with `text` saves an edit of that source's wording; `DELETE …/verses/{id}` resets it to inherited. Every save and reset is kept in `compilation_verse_revision`.
  - **Edits** (`wording.ts`): the user edits plain text, and a word-level diff carries the change back into the source's markup (styles, idiom spans, note marks, breaks; a changed word loses its Strong's attributes). Within the license's `correctionLimit` (3 words or punctuation marks; spacing isn't counted) it's a correction unless the user calls it an adaptation; beyond it, an adaptation. Refused under `no_modification`. The edit keeps a snapshot of the source verse (headings, content, notes) with its hash and import, and shows the snapshot's headings and notes; the editor flags `sourceChanged` when the source verse no longer matches.
  - **Own renderings** (domain-model §2.3.1, `authorship.service.ts`, `journal.ts`, `similarity.ts`): `POST …/journals` (`{reference}`) starts a writing session (from the compilation's own wording, or empty) and notes the translations the editor shows as the study trail; `POST …/journals/{id}/events` adds bursts of writing (`{kind, position, removed, inserted, elapsed?}`), each checked against the text so far and hash-chained to the one before. A paste of at least three words (or a whole verse) from a translation the editor shows is `internal`; any other paste is `external`. `POST …/verses` with `{reference, journal, declaration?}` saves the session's text: an edit of a translation it pasted from (the closest), else `own` with the declaration (the `AUTHORSHIP_STATEMENT` version the user was shown), else `pasted` if it pasted from outside, else refused (`declaration-required`). Own and pasted verses record their similarity to every translation; `POST …/verses/{id}/declaration` declares a pasted one. `GET …/verses/{id}/evidence` downloads the evidence bundle with each journal checked (not yet signed or externally timestamped). Choosing a translation's wording again, or a reset, deletes the verse's evidence.
  - **Translator's notes** (domain-model §2.3, `notes.ts`): an edited verse shows its source snapshot's notes, and an own rendering none, as changed by `compilation_note` rows. `POST …/notes` (`{reference, change}`) makes one change: `{add: {text, after}}` adds an own note marked after the verse's word `after` (at most 20); `{position, text}` rewords a note (a source note becomes `modified`, or unchanged again when reworded as it was; the body keeps its styles and `fr` reference); `{position, after}` moves an own note; `{position, removed: true}` leaves a source note out (recorded) or deletes an own one; `{position, restore: true}` brings back the source's note. A note belongs to its verse: changing one on a verse taken unchanged first makes it an edited verse of its translation (a correction, words unchanged), if the license allows changes. Each change is a revision with the notes. A new edit of the same source keeps the changes to notes it still has; another source keeps only own notes; taking a translation's wording unchanged drops them all. The passage API marks changed notes with `origin` (`modified`, `own`); own notes are in the evidence export.
  - **Resolution** (`resolve.ts`): the verse list and numbering come from the base; for each verse the most specific rule wins (range, chapter, book, section), matched through the canonical scheme. A source verse is used only when it covers exactly the same canonical verses; otherwise the next layer supplies it, down to the base.
  - **Rules:** one reference, whole verses, within the base's text; no overlap with a rule of the same kind; no single verse (that's a single-verse choice). Licenses are checked as data (`@scripturetips/licenses`): `not_as_base` and `no_modification` so far, and an unknown license key allows nothing.
  - **Not yet:** books the base lacks can't take rules (that needs the scheme's own verse lists), and a compilation's language and direction are its base's.
- **Settings** come from the environment (`src/auth/config.ts`; compose.yaml sets them for development). Tests pass their own: `testAccounts()` gives a memory store, a list of sent mail and an easy bot check.
- **Errors are codes, never text** (`unknown-translation`, `no-such-chapter`, `too-many-verses`, `invalid-request` …), with the index where a reference went wrong. The UI words them in the user's language.
- **Compiled, not run from source.** Node can't run decorators from TypeScript, so `tsc -p tsconfig.build.json` writes `dist/`; workspace packages are still loaded from their source. That's why only this app allows non-erasable syntax (`erasableSyntaxOnly: false`); packages Node runs from source must not use it.
- **Inject by token** (`@Inject(TranslationsService)`, `@Inject(DATABASE)`): no decorator metadata is emitted, so constructor types alone don't wire anything.
- **Validation:** Zod schemas through `ZodPipe`.
- **Running it:** `./dev up` starts it with the database, Valkey and Mailpit, rebuilding and restarting on every change, at http://127.0.0.1:3001/api. Logs: `./dev logs api`.
- **Tests:** integration tests through Fastify's `inject` on a test database (packages/db test support).

Run the tests: `./toolbox pnpm --filter @scripturetips/api test`
